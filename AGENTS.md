# MapleTrace agent instructions

Rules and durable decisions for agents working in this repository. How-to material lives in the READMEs listed in [README.md](README.md#docs); do not repeat it here.

## Ground rules

- This is a hackathon prototype. Prioritize a clear, reliable three-minute demo.
- Build the frontend with Vite, React, TypeScript and TanStack Query, and the board with React Flow. Keep backend contracts and disposable fixtures separate from presentation. All case data is fictional.
- Every graph relationship, gap and insight must expose original source citations. Distinguish observed evidence from inference; a gap is not proof.
- Support ZIP upload, ingestion progress, the evidence board, ranked gaps, suggested evidence, source inspection and an audit trail. Keep the board usable on laptop screens with pan, zoom, fit view and a minimap.
- Commit incremental changes with `git commit -S -m "message"`, one signed commit per feature.
- Luna subagents are requested for delegated work. Fetch remote refs at task start and before coordinating or integrating shared work; do not run `git fetch` continuously or poll on a timer.
- Record durable implementation decisions here as work proceeds, replacing lines they make stale.
- Never imply that the mock adapter parses ZIP files or performs real analysis. Keep prototype labelling to upload behaviour and the explicit fictional-case entry points; avoid repeating "demo" in the case workspace chrome. The frontend bundles no real source files or computed hashes.

## Repository layout and tooling

- Keep `AGENTS.md` and the skill installation at the repository root. Frontend files, dependencies, build output and docs live in `frontend/`; backend code, dependencies and docs live in `backend/`; the case generator lives in `generator/`.
- Run Make from the repository root (`make help` lists every target). Do not add nested Makefiles.
- Frontend: Bun 1.4.4, run from `frontend/`. Commit `frontend/bun.lock`; install with `bun install --frozen-lockfile`. Test with `bun run --bun test` (Vitest, not `bun test`), build with `bun run --bun build`, and run `bun run --bun format` after changes. Docker uses the same pinned Bun image.
- Backend: a uv project in `backend/` (`pyproject.toml`, committed `uv.lock`, `.python-version` 3.12; Python 3.11+). It is not an installable package: run commands from `backend/` with `uv run` (the Make targets do). `make backend-install` runs `uv sync --locked` into `backend/.venv`. Add dependencies with `uv add <pkg>` (or `uv add --dev <pkg>` for test-only tools) from `backend/` and commit `uv.lock`; never hand-edit the lock or reintroduce `requirements.txt`. Run `make backend-test` after backend changes.
- Docker and `compose.yaml` are optional. Do not start Docker, run Compose or rebuild images for routine work unless the user asks.

## Backend authority and evidence

- **The backend is authoritative.** Case facts (records, times, entities, citations, hashes) come only from the backend. `case.db` (written by `backend/mapletrace_ingest`), its `ingest_report.json`, and the analysis outputs are the source of truth. `frontend/src/api/types.ts` is a presentation contract: when it and the backend disagree, change the frontend types or adapter, never the backend data. The frontend must not compute, infer or hard-code case facts.
- Ingestion never alters evidence. Working copies are read-only, every file is SHA-256 hashed before parsing, `MANIFEST.csv` hashes are checked, and every step is written to the hash-chained `audit_log`. `python -m mapletrace_ingest verify <run>` must pass. `backend/tests/test_formats.py` re-ingests the Kestrel ZIP and requires every file to parse and every manifest hash to match.
- Every record carries `locator_json` (row, line, `doc_line`, page, JSON path, ...); its file carries `external_id` (the manifest evidence ID). Citations are `{evidence_id, locator}`, written as `EV-071 seq=40162` or source ID `EV-071:seq=40162`. Uncited facts must not reach the frontend. Every citation ID must identify exactly one record: `unique_labels` in `backend/mapletrace_reason/store.py` falls back to the record's position when an ID-like attribute is shared within a file.
- Timestamps are stored in UTC with an uncertainty window and a flag for every assumption. Each file's `time_basis` in `MANIFEST.csv` decides UTC versus local wall time. Human-reported times are `reliability = 'asserted'`, never machine records.
- Identity merges happen only on explicit evidence (contacts, email display names, unambiguous name forms) and are recorded in `entity_links` with a rule and confidence. Fuzzy linkage belongs in the ML stage.
- Media (`mapletrace_reason/media.py`, `vision.py`, contract `backend/MEDIA.md`): every photo and video is an observed board card; links come only from cited rules (VMS export, EXIF device and GPS, MANIFEST.csv custodian and title, facility-directory camera room and same floor during a clip), never from vision text, and never pull cards into `board.story`. Image descriptions (`--llm`) are inferred, live in the separate `llm_cache/vision-<sha>.jsonl`, are attached to media cards only and never reach claims, gaps, insights or the investigator (`backend/tests/test_vision.py`).
- Readable titles (`mapletrace_reason/labels.py`, `label_llm.py`, contract `backend/LABELS.md`): nodes may carry `displayLabel` (≤44 characters), `displaySummary` and `labelOrigin`; sources carry `fileLabel`. Rules labels restate the case's own directory, manifest, contact names and explicit entity links and never add facts; `label` and `summary` never change. Optional LLM labels (`claude-haiku-5-5`, `llm_cache/labels-<sha>.jsonl`, `make backend-label-record`, billed) replay only, skip silently without a cache, fill only cards the rules leave unreadable, and never reach findings or any model input (`backend/tests/test_label_llm.py`).
- Analysis prose names places by `case.place_name()` (`store.py`): "Secure demo cabinet (SC-EBC-01)" when the case's reference lists name the ID, the bare ID otherwise, so text still matches the cited records. Data fields (`places`, comparisons, keys) keep raw IDs. The model's `search_records`/`get_record` outputs use the same form, and the investigator and chat prompts ask for readable names; changing any of this needs `make backend-llm-record` and `make backend-chat-record`.
- Reasoning (`backend/mapletrace_reason`) never writes to `case.db`. Each run writes `analysis/vN/` with `board.json`, `analysis.json`, `graph.json` and `analysis.db`, whose audit chain continues from the ingestion head. Deterministic stages (traditional ML and rules) must work without an API key.
- Traditional ML (`mapletrace_reason/ml.py`) writes cited `signal` items (`ML-xx`) only. Signals go to the board and the agent's `list_ml_signals` tool and are never fed to later stages, so they cannot change findings, explanations or gaps (`backend/tests/test_ml.py` checks this). Models use fixed seeds, learn only from the case's own evidence, and never use protected attributes or the answer key.
- The run trace (`ingest/vN/trace.jsonl`, `mapletrace_ingest/trace.py`, contract in `backend/TRACE.md`) is presentation telemetry: appended while the job runs, never part of the audit chain or the evidence. Its `tMs` is a replay clock: a model response replayed from the cache advances it by its recorded `latency_ms`, or by the estimate in `llm_cache.py` (flagged `estimated`) for older entries. `analysis_mode=live` uploads never read or write the committed cache (case-local `llm_cache/` only). Every board node and edge carries `origin`, `stage` and `evidenceIds`.
- Contradictions list several possible reasons and never conclude that someone lied. Explanations return "insufficient evidence" rather than forcing a verdict. Gaps are typed missing, failed_extraction, conflicting or uncertain. Corroboration counts independent origins, not records.
- Investigator overrides go to `overrides.jsonl` and are applied on every run. Never delete them or the machine result they annotate. Items match across versions by their stable `key`.
- API errors are always `{"error": {"code", "message"}}`.
- Backend run outputs (`backend/runs/`, `backend/data/`) and generated sample ZIPs are not committed.

## LLM layer and cache

- The LLM layer (`--llm`, deepagents) only adds claims and agent insights, and both must cite resolvable record IDs. Models are resolved per role (investigator, chat, vision, labels) in `backend/mapletrace_reason/models.py` from `MAPLETRACE_<ROLE>_MODEL` as `provider:model`; never hard-code a model or provider elsewhere. Defaults: `claude-sonnet-5-5` for the investigator, with chat and vision following it, and `claude-haiku-5-5` for labels. Chat may use a different model from the one that analysed the case. Live calls need the role's provider key; replay needs none.
- Cache keys contain the model, so a different model never replays another's answers. Anthropic models keep their plain name in keys, audit entries and `agent:<model>` labels (`ModelSpec.label`), and default construction must stay byte-identical so the committed caches hit (`backend/tests/test_models.py`).
- Never put upload-form values (such as the case name) into model prompts: replay keys must match across uploads of the same archive.
- Recorded responses are committed on purpose: `backend/llm_cache/<archive sha256>.jsonl` (analysis), `backend/llm_cache/chat-<archive sha256>.jsonl` (chat), and `backend/demo/kestrel.tar.gz` (the finished Kestrel case served by `POST /demo`, which reinstalls a copy whose recorded snapshot hash differs or that lacks `trace.jsonl`, keeping `overrides.jsonl`). After changing anything the model sees, rebuild with `make backend-llm-record` (billed), `make backend-demo-snapshot` (free) and `make backend-chat-record` (billed).
- Tool names, docstrings (whitespace included) and outputs in `llm.read_tools` are part of the cache keys of both the investigator and chat caches. Editing them invalidates both. So do installed packages that change deepagents' built-in tool schemas: never add PyAV (`av`) to the backend, because it rewrites the `read_file` description.

## Case data and generator

- Generated data under `cases/` is the authoritative data for backend work. Never hand-edit it: change `generator/`, run `make data-generate`, and confirm with `make data-verify` (byte-for-byte check against `BUILD_INFO.json`). The generator needs Python 3.12+ and uv; its pins are the PEP 723 block in `generator/generate.py`.
- Frontend fixtures (`frontend/src/api/fixtures.ts`) are disposable mocks. Never use them as a backend data source or reconcile backend data to them.
- `cases/kestrel/evidence/` and `kestrel_case_upload.zip` are the pipeline inputs. The repository holds no answer key. `make data-truth` writes one to the git-ignored `.truth/kestrel/` for scoring only. Never commit it, and never give it or anything under `generator/` (which encodes the solution) to the model.
- All people, companies, numbers (555-01xx), plates and domains (`.example`) are fictional. Do not add real people or organizations to case data.
- Protected attributes (for example `id_issuing_country`, nationality) must never be model features or be returned by the API. The case includes a deliberate bias trap (RH-03).

## Frontend decisions

### Adapters and data

- API seam: `CaseApi` in `frontend/src/api/types.ts`. `http.ts` is the live adapter for `backend/mapletrace_api`; `client.ts` selects it from `VITE_API_BASE_URL` (development defaults to `/api`; `mock`, or an unset value outside development, selects the mock) and owns the mock jobs. UI loads cases by ID through TanStack Query and never imports fixtures directly.
- Mock-only disclosures (ZIP not read, fictional excerpts, illustrative scores and hashes) render only when `api.mode === "mock"`, and the ZIP limitation stays visible beside upload controls. The mock upload validates a `.zip` extension and a nonempty file only, enforces no size cap, and never reads contents.
- Observed versus inferred comes from the API's `certainty` on nodes and edges; claims stay claims. Never infer certainty from edge type names. Arrowheads require API `directed: true`; never reverse an edge from card positions.
- Backend node positions are column placeholders. Live cases use the presentation-only layout `layoutCaseGraph` in `frontend/src/components/graph-layout.ts`: cards cluster by connection, not type (a deterministic force layout per connected cluster, seeded from a radial tree, with 40px clearance on real card sizes), smaller clusters stack beside the main one and unlinked cards line up below. No randomness; fixture positions are hand-placed. Layout code never creates case facts.
- Gap focus uses the backend's `gaps[].nodeIds`; shared citations are only a fixture fallback.
- Backend scores are computed ranks. Show insight `confidence` as a label and ML scores as "Model score 0.xx", never as percentages. Times render in the case `timezone` via `formatCaseTime`.
- Competing explanations show the backend verdict, which may be undecided; never present a hypothesis as a finding.

### Run replay (frontend/src/replay)

- The import and the demo open the empty map and play the run from `GET /cases/{id}/trace` (`useReplay`, default 10x, 1x/10x/50x, pause, skip). `reveal.ts` only decides when an existing board item appears (record nodes at their first parsed `evidenceIds` file, others at their `stage_finished` or `insight_recorded` key, edges when both ends show, everything at `run_finished`); items without provenance and the mock (no trace) show at once. Layout always comes from the full case, so revealed cards never move.
- The start-replay flag is module state (`replay/intent.ts`), not a URL parameter: reloads and later visits show the finished case with a "Replay run" button. A case opened while processing shows the HUD on an empty map, polls the trace every 700 ms and swaps in the board when `GET /cases/{id}` stops returning `not_ready`. Once a case has answered `not_ready` or opened to replay, refetches must not swap the board for the opening spinner (a query with no data returns to "pending" on each refetch); remounting `ReplayedCase` restarts the replay and loses the one-shot request.
- Replay and story view: while a replay grows the board, the full layout fills in and the Story / Full graph switch is hidden. The board is keyed on whether the replay is growing, so when the run ends it remounts with complete data and opens on the story and key finding like a normal load, but animated (`replay/useStoryMorph.ts`, `morph.ts`, `MORPH_MS` 1150 ms): the settled board takes the growing board'- Replay pacing (`buildSchedule` in `trace.ts`) gives every event a wall time; the shown replay clock is always the real `tMs`, interpolated between events. Each run of ingest, rules or ML events takes a minimum on-screen time (3 s, 1.2 s, 2 s at 10x; `phaseMinWallMs`), stated as slowed. Above 1x each gap in the LLM, agent and output phases is eased toward `modelWaitCapMs` (650 ms), stated as "Skipping model wait: N s of waiting shown at X×"; 1x plays recorded waits in full. Events at one instant (the agent's batched tool calls) are spread 60 ms apart (at most 0.8 s per instant), recorded insights 420 ms apart. The recorded Kestrel run (6:51, estimated timing baked into the demo snapshot) plays in about 36 s at the default 10x (was about 50 s). The feed folds consecutive calls of one tool into a counted row; feed times stay the real `tMs`. The HUD counter is "Agent insights" (`insight_recorded` only); the top bar counts revealed insights. Both count up (`CountUp`) as values rise, since rule insights arrive in one stage and the agent's four in one batch. A replay frames the finished layout once at the start instead of refitting as cards appear.gest, rules and ML each get a minimum on-screen time (4 s, 2 s, 2.5 s; `phaseMinWallMs` in `trace.ts`), longer phases use the chosen speed, and the HUD states the effective speed while a phase is slowed. The shown replay clock is always the real `tMs`. The HUD counter is "Agent insights" (`insight_recorded` only); the top bar counts all insights. Bursts of events at one instant (the agent's batched tool calls) are spread across up to 80% of the gap before the next event (`displayTimes`), and the feed folds consecutive calls of one tool into a counted row; feed times stay the real `tMs`. A replay frames the finished layout once at the start instead of refitting as cards appear.
- The HUD labels replay versus live and shows the backend `timing` ("estimated" is never presented as recorded); it collapses to a "Run summary" chip whenever a run ends, and a case opened after its run finished starts with the chip; opening or collapsing it refits the story. Uploads (live adapter) ask for replay or, when `/health` reports `llmLive`, billed live analysis in `UploadConfirm` before sending `analysis_mode`.

While it is expanded the run summary and run panel move right of it, and the Story / Full graph switch drops a row.

The mock lists its audit records instead. It never recomputes or re-verifies the chain.

At 900px and below the stacked dock clears the floating toolbar.
- Keyboard on the board goes through each card's inspect button and each thread's label button; React Flow node and edge focus is off. Focus outlines use `--focus-ring`.
- The frontend may format backend text for display (`formatCaseSubtitle`, audit payload fields) but never changes values.
- The upload modal traps focus and supports Escape when idle or ready; the inspector supports Escape.

### Board

- Evidence cards: Excalifont titles, summaries, question links and thread annotations, with upright sans-serif metadata, a gently uneven paper silhouette, and a centered pushpin 6px inside the top edge. Shapes follow the role (`cardVariant`, sizes in `board-layout.ts`): a person is a small name tag with an initial disc, phones, accounts and places are compact, events, statements, ML/agent/LLM cards and media keep a two-line summary; 40px clearance after placement and drops. Below 60% zoom (`FAR_ZOOM`) cards show titles only and most thread labels wait for hover. Inspection is an arrow-only button with an accessible name; the card shows a pointer cursor; omit inset frames and footer dividers.
- Card titles are `displayLabel` (backend) or else the raw label tidied by `readable.ts` (`k=v; …` pairs and `CODE @ place` reformatted; a pair the backend cut short is dropped, never completed). Whenever the title differs, the raw label stays as small mono metadata and in search, so citations stay traceable; `labelOrigin: "llm"` titles carry the LLM sparkles mark as inferred. Excerpt headings read `fileLabel` (else the file name) `· row 72`, with the citation ID beside it.
- Rendering: node and thread objects are reused while their inputs are unchanged (`createReuse` in `board-render.ts`), card actions go through stable callbacks, and hover reveals labels through one injected stylesheet, so pointer movement never re-renders the board. Cards use a box shadow, not an SVG filter.
- Card colour comes only from API type and certainty, via the inks in `board-colors.ts`: person purple, device blue, event teal, location olive, statement grey. Each thread family shares the hue of its card type. Red means contradiction only.
- Media cards (nodes with `media`, see `backend/MEDIA.md`) keep the event ink and pushpin and put a 4:3 photo or 16:9 clip frame (`<img>`/`<video preload="metadata" muted>` at a mid-duration `#t=` poster, never autoplay, never draggable) under the type row, with a Photo/CCTV chip and a duration badge; sizes live in `board-layout.ts`. The source panel shows the photo or playable clip first, then metadata, then `media.vision` apart as "Description (LLM, inferred)" with the LLM stamp; the replay withholds `media.vision` until `media_vision` finishes (`withheldVision`). The legend lists "Photo / CCTV" when present.
- Inferred cards are dashed with an "Inferred" chip; cards with an open question get an amber outline and flag. Observed threads are solid, inferences dashed `8 7`, claims dashed `3 6`. Every thread label is a source-inspection button showing the relationship wording; its chip edge is dashed (inference) or dotted (claim), and the inferred/claim badge joins on hover, focus or selection (contradictions always). Labels slide along their own thread to the spot covering the fewest cards and labels (`thread-geometry.ts`, contradictions placed first) and sit above ordinary cards; a label with no clear spot folds to a small knot on the thread until its thread or either card is hovered, focused or selected.
- Origin (`origin` on nodes, edges and insights) never changes hue. `ml`, `agent` and `llm` items get a graphite (`ORIGIN_INK`, neutral, 4.5:1 tested) stamp with icon plus word whose form differs by producer ("ML model": scatter icon, dotted outline; "AI agent": bot icon, solid; "LLM": sparkles, dashed outline), a textured strip on the card (dotted, hatched, ruled; down the left edge of story cards), the short model name on ML cards (e.g. DBSCAN, full name in the tooltip and on the expanded story card), the same icon on thread labels, a minimap tab, an "Origin" legend section listing only origins present, and a "Produced by" line in the inspector. `record` and `rules` stay unmarked; items without `origin` render as before. Inferences tab tags each item by origin.
- Colour always travels with an icon, label or pattern, and every ink keeps 4.5:1 contrast against the paper (`board-colors.test.ts` enforces it).
- The legend is a "Key" pill at the bottom right (left of an open dock) that opens a popover listing only the types present; the minimap mirrors the board colours, direction and selection.
- Story view: when `board.story` is present (backend-chosen: the leading key event, the cards around it and those behind the top open questions, at most 12, plus one headline item), the board opens on those cards with a "Story / Full graph" switch at the top of the canvas. Every other card sits in exactly one group card (a story person's contacts, then by type) showing an exact count; group cards, aggregate threads and the story layout are presentation only and never merge or create facts. An aggregate thread names a family or certainty only if it is true of every thread it stands for. Story cards are compact and expand in place (summary, time, up to 3 cited excerpts, Inspect sources, Show connections); expanding pans the view and never moves the layout; Escape collapses. Group cards fan out their members. Specific focus (a gap, insight, suggestion, search or Locate) reveals up to 8 hidden cards; tab-level focus highlights groups instead. Story fits use `getStoryPadding`. In story view the minimap is hidden. Without a story (mock), the board opens as the full graph.
- When `story.headline` resolves, the review dock opens on load on a "Key finding" tab: a status chip (contradiction red, question amber), the title, an asserted statement kept apart from the records, up to 3 supporting sources (asserted first, then one per file), "Review sources", collapsed possible reasons and a not-proof note. Its text is the backend's.
- Minimap (bottom left, zoom controls to its right): frames the pins, and once the view reaches past them frames the pins plus the view, so the viewport rectangle always stays on the map (Excalidraw-style). The map's size follows the pins alone; only the scale changes, easing between framings (instant for reduced motion) and frozen while the rectangle is dragged. Pressing grabs the rectangle or centres the view there; minimap navigation (drag and arrow keys) stays within the pins plus wherever the view already is. The zoom readout sits in the zoom controls.
- The "Ask a question" widget is only a small input with suggestion chips, and typing is always allowed. The chips stay hidden until the widget is hovered or focused, then rise above the box one by one (never moving it, never catching clicks while hidden). In both views the box sits in the board's bottom strip, level with the zoom controls, centred on the visible board but clamped between the left cluster (minimap and zoom controls; story view: the controls alone) and the Key at the bottom right, and its span ends left of an open review dock, so it never covers the minimap, the zoom controls or the Key (`ask-widget.css`). At 540px and below the full graph's strip is too narrow, so there the box spans the board one row above the minimap and controls (the minimap publishes `--minimap-height`). Below 700px the Story / Full graph switch drops below the run summary chip. Submitting navigates to the chat tab, which asks the question; the map never shows answers.

### Insights

- Questions: gaps plus the suggestions tied to them. Evidence: contradictions, cited observations, source groups, missing periods and uncertain times. Inferences, in this order: competing explanations with the backend verdict (top 3 hypotheses, rest behind a toggle), AI agent insights (`origin` agent or llm), ML model leads (every `signals` item, by model score) and rule-based inferences; dashed borders.
- Layout: one sticky header row (the "Insights" h2, tabs with counts, search on the right), then a sticky jump rail listing the tab's sections with counts (each question on Questions) beside the content; the rail hides at 1100px and below. Every item ends in one footer row: its source chips, then Locate on mind map and Inspect.
- Inference cards put the inference first and the backend's observations under "Observed in records" with their own citations; never merge the two. Each item names its producer with icon plus word ("AI agent", "ML model", "Rules", "LLM"); ML leads show the method name and "Model score 0.xx". On the dark panel the origin tag uses light text, not the board's graphite ink.
- ML leads reach the board through the card whose `itemId` matches the signal ID (`EvidenceNode.itemId`); a lead without a card offers its sources only.
- One search covers all tabs (tab counts become match counts); Escape or the clear button empties it, and an empty tab links to the tabs that do match. `insights-sections.ts` only groups API data; it never creates or scores facts.

### Raw evidence and generalized files

- Raw evidence lists files from `GET /cases/{id}/files` and opens them with `GET /cases/{id}/evidence/{evidenceId}/view`. `/evidence/:sourceId` accepts a citation (`EV-xxx:locator`) or a bare evidence ID.
- Positions come only from each record's `locator_json` on the backend. The cited row, line or sentence is highlighted; records sharing a label are marked more lightly.
- Originals are served inline only for images, video, audio and PDF; everything else is a `nosniff` attachment, sandboxed by CSP.
- "Generalized files" means normalized ingestion records: a table whose citations link to the raw file at that row, filtered by type with `GET /records?recordType=`. Never synthesize normalized records from fixture metadata.
- The mock adapter keeps its cited-source list and "unavailable" states.

### Chat

- Implemented. Contract: [`frontend/CHAT.md`](frontend/CHAT.md); code: `backend/mapletrace_api/chat.py` and `backend/mapletrace_reason/chat.py`. Keys stay server-side and the frontend never simulates replies.
- Chat replies carry `steps` (the tool loop); the chat tab replays them as a paced "thinking", tool-call and typing animation, labelled as replayed or live, collapsed afterwards, and instant for reduced motion or history. Step capture must never change what the model sees (cache keys).
- Chat tab layout: the full suggested-question list shows only before the first question; afterwards an "Ask next" row above the composer offers the questions not yet asked. A new question scrolls to the top at once (a spacer gives it room until its answer fills in), and suggestions and sending wait until the playing answer finishes. Each answer's full "Cited excerpts" list is collapsed; observations keep their citation chips.
- Suggested questions are deterministic and always answered without thread history, so they replay. Free typing is live and billed and needs a server key; without one the server only replays, and a miss returns `needs_api_key`.

### Brand and visual design

- Tokens and the full design system live in [`frontend/DESIGN.md`](frontend/DESIGN.md); `SPEC.md` is the single product spec and Impeccable product context (do not create a `PRODUCT.md`). App-specific Impeccable settings live in `frontend/.impeccable/`. Impeccable work is frontend-only; if its loader misses `SPEC.md` or the frontend artifacts, read them directly instead of reopening init. Future landing pages use the confirmed code-first workflow.
- The product name is `MapleTrace` in all UI, titles and tokens; snake_case package names (`mapletrace_ingest`, ...) stay as they are.
- The mark is `frontend/public/mapletrace-mark.svg`, rendered inline by `BrandMark.tsx`. Use it on dark surfaces only, never recolour it, and never use stock icons as a stand-in logo.
- Blue (`--brand-*` in `src/styles/base.css`) means interaction, selection and focus; amber means open questions; status greens and reds stay separate. `--green` is a legacy alias of the brand blue; migrate away from it.
- Glass (`--glass-fill`, `--glass-edge`, blur) is for chrome only, never for reading surfaces, cards or the paper canvas.
- Dark workspace chrome surrounds a faint paper canvas. Non-board sections render in framed floating panels with 16px clearance. Corner radius is for structural floating containers (toolbar, panels, dock, cards), not icons, chips or internal boundaries.

## Docker

- The backend image is built from the repo root and mirrors the repo layout under `/app`. The root `.dockerignore` is an allowlist: add any new runtime file to it.
- Data lives in the `mapletrace-data` volume at `/data`; the image runs as a non-root user.
- The frontend image is built with `VITE_API_BASE_URL=/api` (`mock` is a build arg). Caddy serves the frontend and strips `/api` the way Vite does; its `max_size` must follow `MAPLETRACE_MAX_UPLOAD_MB`.
- Only the frontend is published, on `127.0.0.1:5173`. `ANTHROPIC_API_KEY` and `GOOGLE_API_KEY` are optional.

## Vultr deployment

- Run Vultr deployment and its tests from the root with `make vultr-deploy` and `make vultr-test` (uv); pass non-secret options in `VULTR_ARGS`.
- `scripts/deploy-vultr.py` deploys committed revisions to a single Ubuntu instance using `scripts/compose.vultr.yaml`. Caddy provides automatic TLS for the configured domain (default `mapletrace.work`); the app remains unauthenticated. Case data uses a mounted Vultr block storage volume; Caddy certificates stay in a Compose volume. The deploy workflow provisions or reuses a Vultr firewall, instance, block volume and Object Storage bucket, reads optional deployment settings from git-ignored `scripts/.env`, records resource IDs locally for retries, and uses daily object-storage case backups with backend writes stopped during archiving. A scoped 60-day lifecycle expires backups. Keep the deploy upload limit aligned with Caddy.
